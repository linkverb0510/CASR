# CASR 实验设计与执行路线（V1.0）

> 本文记录当前实验计划。数据规模、基线和指标均为拟议方案，需在复现与预实验后调整。

## 1. 实验目标

检验 CASR 是否能在 Coding Agent 接受中途用户更正后：

1.  更好地满足更新后的有效需求；
2.  保留此前仍然正确的功能；
3.  减少旧计划复发和不必要修改；
4.  降低修复成本及回归风险。

核心比较不是单纯的最终任务成功率，而是**新需求满足与既有功能保留能否同时改善**。

## 2. 数据集与任务构造

### 首选起点

**SWE-Interact**：作为交互式 Coding Agent 任务来源和实验环境候选。

使用前需核对论文、官方代码和许可，确认具体任务是否支持本研究需要的中途更正、工作区状态检查和可重复执行。不能假定原始数据集已经完整覆盖
CASR 场景。

### 初期规模

-   原型阶段：先构造或筛选 10--15 个高质量案例，跑通端到端流程。
-   扩展阶段：在流程稳定后，争取形成 30--50 个案例。
-   上述数字是规划目标，不是现成基准的既有规模。

### 更正类型

  类型          含义                     示例
  ------------- ------------------------ -----------------------------
  ADD（对照）   新增要求，不撤销旧要求   增加日志输出
  AMEND         修改已有要求             改变实现方式或参数
  REVOKE        撤销原有要求             不再实现某项功能
  SUPERSEDE     新要求替代旧要求         禁止 pandas，改用标准库 csv

### 每个案例应记录

1.  初始任务和初始代码仓库；
2.  更正前 Agent 的执行轨迹；
3.  用户更正发生的时间点及原文；
4.  更正后的有效需求；
5.  预期受影响的动作和产物；
6.  应当保留的原有功能；
7.  自动化验收测试及必要的人工标注。

应尽量保存更正前的工作区快照、Git
Diff、工具调用记录和测试结果，以支持复现与对照。

## 3. 对照实验（Baselines）

  编号   方法                     对照目的
  ------ ------------------------ --------------------------
  B0     Vanilla Agent            原始 Agent 能力
  B1     Full History + Prompt    仅依靠完整历史和最新更正
  B2     Requirement Ledger       显式维护需求状态
  B3     State / Impact Harness   项目状态与变更影响跟踪
  B4     Checkpoint Rewind        整体回滚后重新执行
  Ours   CASR                     依赖感知的选择性修复

实现 B3 时，应选择并复核合适的现有方法作为参照，例如 StateHarness。TRACE
可作为规则编译与运行时约束执行的相关基线或组件参考。

公平比较时，尽可能固定基础模型、Agent
Harness、工具权限、初始仓库、用户更正内容和测试环境，并记录模型版本、提示词、采样参数及运行成本。

## 4. 核心评价指标

  ----------------------------------------------------------------------------------------------
  指标                    建议定义                                       方向
  ----------------------- ---------------------------------------------- -----------------------
  Active Requirement      满足的可评估有效需求数 / 可评估有效需求总数    越高越好
  Conformance                                                            

  Retained Functionality  修复后仍通过的、此前已验证且仍适用的功能数 /   越高越好
                          此类功能总数                                   

  Repair Success          同时通过新需求验收和保留功能验收的案例比例     越高越好

  Stale Action Rate       更正后仍执行、且与新要求冲突的旧计划动作比例   越低越好

  Collateral Edit Rate    经标注为不必要的修改产物数 / 全部修改产物数    越低越好

  Repair Cost             Token、工具调用、测试次数、耗时等              越低越好
  ----------------------------------------------------------------------------------------------

指标计算前必须明确分母、不可评估样本处理方式和人工标注规范。不同案例之间应使用一致的定义。

## 5. Verifier 评价

验证器本身也必须接受评测，至少报告：

-   Precision：被判定为违规的结果中，真实违规的比例。
-   Recall：真实违规结果中，被验证器发现的比例。
-   False Acceptance：错误结果被判定为通过。
-   False Rejection：正确结果被错误判定为失败。
-   UNKNOWN Rate：证据不足、无法可靠判定的比例。

建议结合隐藏测试、替代有效实现、重复运行、人工抽样和必要的 mutation
testing 检查验证器可靠性。不能把 LLM 自评直接当作真实环境证据。

## 7. 预期结果与判断标准

不预设虚构的提升百分比。重点观察：

-   新需求满足率是否提高；
-   原有有效功能保留率是否同时提高；
-   是否减少不必要修改和旧计划复发；
-   修复成本是否可接受；
-   Verifier 是否有足够低的误接受率和误拒绝率。

如果只提高新需求满足率，却明显破坏原有功能，则不能认为 CASR
已经解决核心问题。

## 8. 执行路线

### Phase 1：Related Work 与问题形式化

-   精读 StateHarness、AgentRewind、TRACE 和 Long-Horizon SWE 综述；
-   明确 CASR 与现有方法的差异；
-   定义需求、动作、产物、证据的数据结构；
-   写清更正类型和修复决策规则。

**交付物：** Related Work 对比表、Problem Definition、数据结构草案。

### Phase 2：Benchmark 与最小原型

-   筛选或构造中途更正案例；
-   实现 Requirement Ledger；
-   记录执行溯源；
-   构建初版关联图；
-   实现影响分析、修复规划和 Verifier。

**交付物：** CASR V0 可运行原型及 10--15 个端到端案例。

### Phase 3：基线与消融

-   跑通 Vanilla Agent 和状态管理基线；
-   对比整体回滚与选择性修复；
-   运行消融实验；
-   分析失败案例和验证器误判。

**交付物：** 第一批实验结果、误差分析和方法修订。

### Phase 4：优化与论文

根据 Phase 2--3 的结果决定是否：

-   改进影响传播和修复规划；
-   扩大任务规模；
-   研究 Verifier-Guided DPO；
-   进一步探索 Agentic RL。

**交付物：** 完整实验、论文初稿及可复现实验材料。

## 9. 主要风险

  --------------------------------------------------------------------------------------------
  风险                                应对
  ----------------------------------- --------------------------------------------------------
  需求与动作关联提取不准              结合工具日志、Git Diff、静态分析和 LLM，抽样核验

  影响传播范围过大                    区分失效、受影响待验证和无关节点

  修复破坏原功能                      保存快照，执行保留功能测试

  Verifier 误判                       隐藏测试、人工抽样、重复性和 mutation testing

  方法过于复杂                        先完成最小闭环，再逐步增加模块

  与已有 Harness 工作重叠             聚焦"用户更正触发的选择性修复"，通过基线和消融证明差异
  --------------------------------------------------------------------------------------------

## 10. 当前明确不做的事

-   不在没有可靠验证器前直接开展 DPO / RL；
-   不同时扩展到 GUI、Data Analysis 或通用多 Agent；
-   不把单纯增加 Memory、Ledger 或依赖图当作充分创新；
-   不仅凭 Agent 自述判断任务完成；
-   不以单一最终成功率替代功能保留和回归评测。
