# CASR 研究问题与方法框架（V1.0）

> 状态：研究方向、应用场景与总体技术路线已冻结。具体算法设计和有效性仍需实验验证。

## 1. 研究定位

**英文题目：** Correction-Aware Selective Repair for Long-Horizon Coding
Agents\
**中文题目：** 面向长程编码智能体的更正感知选择性修复

  决策维度   冻结选择
  ---------- -----------------------------------------------
  应用场景   Long-Horizon Coding Agent
  核心问题   用户更正触发的 Selective Repair
  技术路线   Harness + Verifier
  后续扩展   在验证器和数据可靠后，再考虑 DPO / Agentic RL

## 2. 研究问题

当用户在长程编码任务执行过程中修改、替代或撤销要求时，Agent
如何基于执行依赖关系，定位受影响的历史动作与代码产物，进行最小必要修复，同时满足更新后的需求并保留此前仍然有效的功能？

### 典型场景

Agent
已根据初始要求执行了多个步骤、修改了若干文件。用户随后改变实现方案或撤销某项要求。Agent
需要判断：

1.  哪些旧需求或计划已经失效？
2.  旧计划已经影响了哪些动作、文件和后续步骤？
3.  哪些内容需要撤销或修改，哪些需要重新验证，哪些应当保留？
4.  如何验证新需求已满足，且原有有效功能没有被破坏？

## 3. 核心假设

用户更正通常只会使部分历史执行行为及其产物失效，并不意味着整个历史执行过程都需要推翻。

如果建立需求、执行动作与代码产物之间的关联关系，Agent
就有机会更准确地定位更正影响范围，减少不必要的回滚和重复执行，并在满足新要求的同时保留有效工作。

这是待检验的研究假设，不是已经得到证明的结论。

## 4. 方法框架：CASR

CASR 暂定由四个模块组成。

### Module 1：Requirement State Management

维护需求及其生命周期：

-   Active Requirements：当前有效的需求。
-   Superseded / Revoked Requirements：已被替代或撤销的需求。
-   Requirement Versions：需求的版本和变化记录。

目标是得到用户更正后的当前有效需求状态。

### Module 2：Execution Provenance Graph

建立需求、执行动作、代码产物和验证证据之间的关联图。

建议节点：

  节点          内容
  ------------- ----------------------------------
  Requirement   用户需求及其版本
  Action        Agent 计划、工具调用、执行步骤
  Artifact      文件、代码模块、配置、测试等产物
  Evidence      测试结果、命令输出、验证记录

建议关系：

-   `Motivates`：需求促成某项动作。
-   `Produces`：动作产生某个产物。
-   `Depends-on`：产物或动作之间存在依赖。
-   `Validates`：验证证据支持某项需求或产物。

数据来源采用混合方式：工具日志、Git Diff、文件读写记录、静态分析，以及
LLM 辅助提取语义关联。关键关系应尽可能通过规则检查或人工抽样核验。

### Module 3：Dependency-Aware Selective Repair

根据更正影响范围，对历史工作进行分类：

-   **Revert**：撤销已经失效的修改。
-   **Modify**：修改仍需保留但不符合新要求的产物。
-   **Revalidate**：重新验证可能受到影响的产物。
-   **Retain**：保留不受影响且仍然有效的工作。

目标是生成最小必要修复计划，而不是默认整体回滚或从头重做。

### Module 4：Independent Verifier

验证修复结果：

-   当前有效需求是否满足？
-   原有且仍适用的功能是否保留？
-   是否继续执行与新要求冲突的旧计划？
-   是否引入新的回归问题？

验证结果可分为：

-   `PASS`：证据足以支持通过。
-   `FAIL`：发现明确违规或失败。
-   `UNKNOWN`：证据不足，需要进一步检查或人工确认。

## 5. 预期研究贡献

以下是拟验证的贡献方向，不应在实验前宣称已经成立。

1.  **Correction-Triggered Impact
    Propagation**：研究如何将用户更正传播到历史动作和代码产物，定位影响范围。
2.  **Dependency-Aware Selective
    Repair**：研究如何依据影响关系，选择性撤销、修改、重新验证或保留历史工作。
3.  **Retention-Aware
    Verification**：建立同时关注当前需求满足与原有有效功能保留的验证机制和评测方案。

主要方法创新聚焦前两项；第三项作为支撑方法和实验贡献。

## 6. 研究边界

V1.0 聚焦：

-   本地代码仓库中的长程编码任务。
-   Agent 执行中途发生的需求修改、替代或撤销。
-   需求、动作、产物之间的影响追踪。
-   选择性修复及修复结果验证。

暂不作为首阶段重点：

-   跨会话用户偏好学习。
-   GUI / Computer-Use Agent。
-   分布式多 Agent 协作。
-   不可逆外部 API 操作。
-   以 DPO / RL 训练为起点的端到端方案。

## 7. 与后续训练的关系

当前 V1.0 采用 Harness +
Verifier，先证明状态追踪、影响分析和选择性修复有效。

后续可探索：

-   **V2.0：Verifier-Guided DPO**。用验证结果构造 Chosen / Rejected
    修复轨迹。
-   **V3.0：Agentic
    RL**。在可执行环境中优化修复质量、功能保留和修复成本。

只有当验证器的可靠性得到检验后，才考虑将其输出作为训练监督信号。
